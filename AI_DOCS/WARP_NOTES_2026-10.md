# WARP: эталонный паттерн и мониторинг обрывов (2026-10-10)

Зачем: у части людей WARP стал падать с `CF_HAPPY_EYEBALLS_MITM_FAILURE`
(«CF_HAPPYFAIL»); смена протокола помогает на время, потом снова рвёт.
Нужен эталон «куда летит рабочий WARP», чтобы сравнивать логи людей с
обрывами и понять, наш ли это класс (ТСПУ/оператор) или сторона Cloudflare.

## Клиент (наша машина, эталон)
- `warp-cli 2026.6.850.0`, режим `Warp`, протокол **MASQUE** (H3 с фолбэком H2),
  post-quantum `P256Kyber768` (EnabledWithDowngrades).
- PMTU туннеля **1353**, DNS `1.1.1.1`/`cloudflare-dns.com`.
- Пороговые эвристики самого клиента: loss 5%, latency 250 мс - при устойчивом
  превышении клиент сам уходит в реконнект (смена порта/эндпоинта).

## ПАТТЕРН рабочего WARP (что и куда летит)
- Внешний транспорт: **QUIC (MASQUE) по IPv4 UDP**, локальный эфемерный порт →
  `162.159.198.2:443` (основной), кандидат `162.159.197.4`
  (в конфиге anycast-split: *.197.3 always_exclude, *.197.4 always_include).
- При happy-eyeballs клиент перебирает порты: **443, 500, 1701, 4443, 4500,
  8095, 8443** (и secondary-протокол H2) к тому же эндпоинту - это видно в
  `cfwarp_service_log.txt` прошлых сессий.
- Живой захват (2026-10-10, tethering, Wi-Fi): за 15 с ~927 исх / ~1040 вх
  строк (с дублями стека), размеры 42-44 Б + данные:
  `192.168.117.169.64052 > 162.159.198.2.443: UDP, length 42`
  `162.159.198.2.443 > 192.168.117.169.64052: UDP, length 44`
- Метрики здоровья (норма): edge_rtt ~30-40 мс, loss ~0.006%, colo **HEL**.

## Как снять у себя
- `warp-cli status` / `settings` / `stats`;
- pktmon (admin): фильтры по remote-IP `162.159.197.4` и `162.159.198.2`
  (`pktmon filter add wre -t UDP -i 162.159.198.2`) - ловит туннель надёжно
  (локальный порт меняется, remote - нет);
- наш probe на `warp-svc` - см. оговорку ниже.

## Как мониторить у ДРУГИХ (кому рвёт)
1. `warp-cli status`, `warp-cli stats` + скрин ошибки.
2. Логи (стандартный support-пакет Cloudflare):
   `%ProgramData%\Cloudflare\`:
   - `cfwarp_service_connection_stats.txt` - раз в 30 с QUIC/туннель статы:
     `client_packets_sent/recvd`, `lost`, `pto_count`, `edge_rtt`;
   - `cfwarp_service_log.txt` - события happy-eyeballs/MASQUE/эндпоинты;
   - `qlogs\` - QUIC-трейсы.
3. В момент обрыва - наш контрольный логгер (пинг/шлюз/DNS): если всё чисто,
   а WARP падает - фильтруется сам UDP-транспорт, не общий канал.
4. Probe на `warp-svc` - как дополнение.

## Признаки «путь режут» (по статам/логу)
- `client_packets_sent` растёт, `recvd` стоит; `client_total_pto_count` растёт;
- rtt/edge_rtt скачут к секундам; в логе - happy_eyeballs fail
  (`CF_HAPPY_EYEBALLS_MITM_FAILURE`) и реконнект-штормы;
- захват: исходящие есть, входящих ноль.

## Оговорка закрыта: «UDP 0/0» был багом НАШЕГО парсера (2026-10-10)
Первый прогон probe на `warp-svc` дал «UDP 0/0» при живом туннеле. Причина -
не поздние pktmon-фильтры, а парсер `_parse_pktmon_txt`: он резал строки
etl2txt по ПЕРВОМУ `>` (на Wi-Fi строка начинается с MAC-пары
`B4-0E-.. > 26-21-..`), и все UDP-пакеты отбрасывались. Исправлено (regex с
якорем `: UDP`). Ретест на живом WARP после фикса:
`162.159.198.2:443 - пакеты 14967 -> 16860` (UDP), плюс замечен висящий
`162.159.36.1:53 SynSent` (TCP-53/DoH режется у оператора). Баг касался
ВСЕХ Wi-Fi-машин - это же объясняет «UDP 0/0» в логах Ace Combat; фикс
важен не только для WARP.

## Гипотеза общей причины (связанные кейсы)
- Финка Discord (GCP `35.217.x:50002`): режется ВХОДЯЩЕЕ направление UDP.
- Ace Combat 8 (`UN-408`): таймаут логина при живых CDN/TCP.
- WARP: обрывы UDP-транспорта к Cloudflare-эндпоинтам (5-15 мин цикл).
Общий знаменатель: оконная деградация UDP к зарубежным облакам; TCP не
страдает. WARP как VPN-паттерн может детектиться агрессивнее; смена протокола
= смена сигнатуры → «пробило, потом отвалилось».

## Эксперимент на будущее
Завести «игру WARP» в games.json (порты 2408/500/1701/4500 + подсети
эндпоинтов Cloudflare) с игровым рецептом `fake:payload=all` - проверить,
продлит ли наш обход жизнь WARP-флоу (по аналогии с играми).

## Пересечения с нашим обходом (порты/профили)
Наш движок НЕ блокирует - только добавляет десинк/фейки к своим пакетам.
Окна: TCP `80,443,2053,2083,2087,2096,8443`; UDP `443,19294-19344,50000-50100`
(+порты игр при GameFilter).

| WARP-транспорт | В нашем окне? | Трогаем ли десинком |
|---|---|---|
| MASQUE UDP 443 → 162.159.198.2 | да | НЕТ: QUIC-профиль требует hostlist-имя, а туннель идёт на IP-литерал (без DNS) → мимо |
| fallback UDP 500/1701/4443/4500/8095/8443 | НЕТ | движок их не видит вовсе |
| WireGuard UDP 2408 (если протокол переключат) | НЕТ | не видит |
| TCP control/API (`*.cloudflareclient.com` - есть в list-general!) | да | ДА: General-профиль десинкает control-трафик (fake+multisplit). На нашей машине не мешает; теоретически может и маскировать |
| DoH на 162.159.36.1:443 (SNI cloudflare-dns.com) | да | по спискам не матчится (домена нет в списках) → мимо |
| **GameFilter=udp/both** (тоггл) | окно → 1024-65535 + catch-all `fake:quic_google:repeats=10:payload=all` | ДА: фейки полетят и в туннель (443 и все fallback ≥1024) - единственный сценарий активного вмешательства |

Выводы:
- «Невписанный порт» разрывов НЕ вызывает: без покрытия трафик просто идёт
  как без обхода. Но и защиты на этих портах тогда нет (если DPI душит
  WARP-флоу на fallback-порту - мы бессильны, отсюда идея «игры WARP»).
- При включённом GameFilter наш обход начинает лить фейки в сам туннель -
  включать его при активном WARP без понимания не стоит.
