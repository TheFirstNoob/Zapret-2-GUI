## 1. tspu-docs — как реально работает ТСПУ (EcoFilter)

### Блокировка HTTPS = только по SNI (17.5.3, 5.1.5)
- Client Hello содержит SNI = только домен, без пути. URL/путь в HTTPS не видны.
- HTTP: блок → редирект 302 на заглушку. HTTPS: содержимое зашифровано → RST.

### `send RST off` — ВСЕГДА включён в проекте (17.1.2) 🚨
- Reset при блокировке НЕ шлётся. Соединение дропается МОЛЧА, «висит» до таймаута.
- Это ровно наш симптом (000/таймаут, «Discord виснет на Starting»), а не мгновенный RST.
- Причина: при RST-блоке мессенджеры бесконечно реконнектят → нагрузка на фильтр.

### Деградация протоколов (17.3): capacity 0-100
- 0 = полный блок, 100 = полный пропуск, 1-99 = **вероятностный дроп пакетов**.
- Эффективно «заметно» только при 2-10 (TCP компенсирует потери сам).
- **Вывод для нас:** «репиты пробивают» может работать против вероятностного
  дропа — заваливание пакетами повышает шанс прохода. И «плавающие» 000 —
  следствие вероятностного дропа, тесты надо повторять (правило §29 уже есть).

### DPI-листы: blacklist/whitelist, behavior block/ignore/color/redirect (17.4)
- blacklist (default) — совпало со списком → действие; whitelist не используется.
- No IP / No IP Remote — исключения абонентов/серверов (для диагностики).

### Двухстадийная блокировка (8, 23.3) — «5-15 минут»
- Этап 1: фильтр распознаёт протокол (behavior: ignore), логи → SPFS → ЦСУ.
- Этап 2: ЦСУ собирает логи со ВСЕХ площадок (~350, ~5000 устройств), очищает
  от ложных срабатываний, формирует списки IP+порт → загружает на фильтры (HTTP)
  и Eco Highway (BGP).
- Полный цикл: 5-15 минут. До обновления списка существующие сессии не рвутся.
- **Вывод:** блоки «плавают» во времени — то работает, то нет (мы это видим).

### DPI Engine: многофакторный анализ СЕССИИ, не пакета (23.1)
- Параметры: размеры пакетов + вариации, частота/интервалы, паттерны, размеры.
- Для шифрованного трафика — только КОСВЕННЫЕ статистические признаки.
- **Вывод для нас:** наш фейк+повторы меняют «профиль сессии» (размеры/частоту)
  на google-подобный → классификатор путается. Не «тупая долбёжка».

### Обфускация и гонка вооружений (23.4)
- «Постоянное противостояние»: обход → новая сигнатура → новый обход.
- Таблица: простая обфускация → распознаётся; притворяется другим → сложно;
  **качественная имитация → распознать НЕВОЗМОЖНО** без нового подхода.
- **Вывод:** repeats — тактический выигрыш (паттерн «всплеск одинаковых пакетов»
  тривиально маркируется). Вектор — имитация реального трафика
  (tls_client_hello_clone, tls_mod=rnd,dupsid, oob).

## 2. b4 — механики обхода (Go, Linux), что взять для lua

### SNI-first в ClientHello — критично для ТСПУ (tlsgen/generator.go) 🚨
> «GenerateTLSClientHello with SNI as the FIRST extension. This is critical for
> bypassing Russian TSPU DPI systems which use fast-path optimization for
> whitelisted domains when SNI appears first.»

Проверка НАШИХ блобов (SNI позиция в списке расширений, 0-based):
| Блоб | размер | расширений | SNI позиция |
|---|---|---|---|
| tls_clienthello_www_google_com.bin | 681 | 17 | **0** (first) ✅ |
| tls_clienthello_max_ru.bin | 664 | 15 | **0** (first) ✅ |
| tls_clienthello_web_max_ru.bin | 238 | 9 | **0** (first) ✅ |
| tls_clienthello_sochi_park.bin | 244 | 6 | **1** (после 0xd sig_algs) ⚠️ |

**Вывод:** google/max_ru/web_max_ru — SNI-first (как и требует b4). sochi_park —
НЕ first (выбран в GUI fake_blob!). Если где-то не пробивает — проверить блоб.
Возможно стоит генерировать блобы через SNI-first (наш tools/make_blob.py
должен это поддерживать / проверить порядок расширений).

**Проверено (2026-09-10):** наш `tools/make_blob.py` уже генерирует SNI-first
(строка 59: `exts += _sni(hostname)` — SNI первым расширением) + синтетический
key_share (сервер отбросит приветствие). Структура соответствует b4 tlsgen.
Готовый тест-пресет `test-snifirst.txt` (discord-блоки на sochi_park, SNI pos 1)
— чтобы проверить, влияет ли позиция SNI на пробиваемость.

### Десинк «наоборот» — фейки RST/FIN/ACK (nfq/desync.go)
- Каждый фейк с ИСПОРЧЕННОЙ TCP-суммой (`corruptTCPChecksum`) — сервер дропает,
  DPI читает. (У нас в lua: `reconstruct: badsum`?)
- **Динамический TTL** (`dynamicTTL`): TTL фейка ≤ реального TTL пакета,
  иначе «невозможное значение» маркируется DPI. (У нас: `ip_autottl=delta,min-max`.)
- Разные seq: RST с seq-10000/0/+10000; ACK futureSeq (rand) / futureAck
  (orig+100000*i), TTL убывает с каждым фейком.
- **combo = RST+FIN+ACK** (последовательность с задержками 50-500 мкс).

### RST protection (README)
- «Detects forged resets by TTL/flag/option fingerprint and drops them» —
  в winws2/lua такого НЕТ. Идея: поддельные RST от DPI отличаются по TTL/флагам/
  опциям — можно дропать их (защита от RST-блока).

### Остальное в b4 (не переносится 1-в-1, но идеи)
- QUIC: sniff/parse/assemble (src/quic) — наш движок уже делает quic fake.
- MTProto proxy + Telegram-over-WebSocket (src/mtproto) — вне зоны движка.
- DNS: redirect to DoH, fragmented queries, DNS-over-TCP (src/dns) — у нас hosts.
- Discovery/Watchdog/Detector — авто-подбор стратегии (у нас тестер + вердикт).
- Escalation chains — при нестабильности хост переходит на более тяжёлый пресет
  (у нас auto.txt circular — похожая идея).
