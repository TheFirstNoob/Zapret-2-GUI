## 2. Методология (3 итерации — важно не откатить!)

1. **v1 (ошибка):** пробы шли ПОД работающим десинком — с включённым ipset
   пробные IP лежали в ipset-all, наш fake+multisplit применялся к белым SNI →
   смесь «ТСПУ + наш обман».
2. **v2 (текущая):** скан сам глушит защиту (`_run_asn_scan`: kill +
   `asn_scan()` + сервис-осведомлённый `_restore_protection_after_naked`),
   конкурентность 4 (пачки SYN в один ASN будят антискан хостеров), curl `-S`,
   exit 28 классифицируется по stderr (CONNECT-фаза = SYN DROP; общий таймаут =
   TIMEOUT), «не отвечает» подтверждается повтором через 1.2с.
3. **Ценность скана — диагностическая** (объяснить «почему X не работает»),
   НЕ самоулучшение. Кнопка остаётся, фича не рекламируется; список IP
   протухает — обновлять из репо dpi-detector через jsDelivr.

## 3. Чистый замер на Т2 СПб (мобильный, 06.09 вечер) — выводы

Один вечер — четыре разные картины (97/110 → 18/110 OK): ТСПУ/транзит Т2 к этим
ASN флапает по десяткам минут; одиночный скан = снимок, не приговор.
- Наши короткие curl-POST «проскальзывают» чаще (66-84 OK), их длинные
  keep-alive потоки режутся раньше (18 OK) — разные инструменты меряют разную
  экспозицию; сравнивать надо динамику ОДНОГО инструмента.
- SYN DROP-набор совпадает с ipset-«ломает»-набором: наш десинк реально ломает
  белый SNI-хендшейк к этим диапазонам (curl виснет в SSL_connect, raw socket
  connect проходит) — ярлык «SYN DROP» условен («TLS-фаза, сервер/ДПИ молчит»).
  Не тратить время на «оживление» этих IP списком.
- CDN77 флапает часами (OK → DROP → OK).
- Теория (не проверена): вечерняя деградация — реакция ТСПУ на активность
  сканирования. Практика: (а) не сканить часто подряд; (б) после жирного скана
  первые замеры пессимистичны — пауза час-два.

## 5. dpi-detector — как пользоваться

Готовый exe в releases (или `pip install "httpx[socks,http2]==0.28.1" h2 hpack
socksio rich PyYAML`); запуск: `python dpi_detector.py -t 34 --batch -o report.txt
-c 30` (НОРМАЛЬНЫМ python, не pythonw — TUI рисует rich-таблицы).
Тесты `-t`: 0=инфо, 1=DNS-серверы, 2=домены (TLS/HTTP), 3=**TCP 16-20KB по 110 IP
(tcp16.json)**, 4=белые SNI по заблокированным ASN, 5=Telegram, 6=легенда.
config.yml: TCP_BLOCK_MIN_KB=12/MAX=36, FAT_DEFAULT_SNI=example.com,
CONNECT/READ_TIMEOUT=8 (FAT_READ=12), MAX_CONCURRENT=50.
Данные протухают: tcp16.json, whitelist_sni.txt, domains.txt.
Наш аналог — asn_scan (упрощён: один белый SNI, POST 32KB, concurrency 4, чистый
путь). Их плюсы: chunked-детект с фазами, перебор SNI по ASN, DNS-таблица.

## 8. Сравнительный прогон: наш asn_scan vs dpi-detector (07.09, Т2 моб.)

| Прогон | Их dpi-detector (-t 3, c=30) | Наш asn_scan |
|---|---|---|
| чистый путь и под защитой | 18/110 OK (16%) — идентично | 84/110 OK (26 SYN DROP) — идентично |
| скорость | ~2-3 мин | 53с (было 192с: --connect-timeout 3 + concurrency 8) |

**Выводы:** (1) защита/блоб НЕ влияют на ASN-IP тест (белый SNI вне hostlist) —
методика «чистого пути» избыточна; (2) разница 18 vs 84 — экспозиция, не
качество: их chunked keep-alive ловит «ответ не пришёл» как TIMEOUT, наш
single POST честно разделяет «поток ушёл» (OK) и «SYN не встал» (SYN DROP);
(3) их DETECTED 1/110 — наш POST проскочил, не критично.

**Батарея SNI (07.09, чистый путь, 110 IP × 5 SNI):**
| SNI | Результат | Вывод |
|---|---|---|
| example.com | **104/110 (94%)** | IANA-домен, в реестре быть не может — лучший зонд |
| www.sferum.ru (VK) | 100/110 (91%) | российский «белый» |
| hcaptcha.com | 84/110 (76%) | субоптимально (был наш прежний) |
| www.google.com | 79/110 (+5 TLS RST) | гигант — фильтры плотнее |
| rutracker.org (ЧЁРНЫЙ) | **0/110 — все SYN DROP** | контроль: ТСПУ режет по SNI даже чистые VPS-диапазоны |

**Вывод:** SNI — переменная первого порядка. Дефолт ASN_SNI сменён на
example.com; `asn_scan(..., sni=...)` параметризован.

**Клиент-фингерпринт (curl vs httpx, 46 доменов):** 42/46 совпали, расхождения —
пороги таймаута и флак, НЕ фингерпринт. ТСПУ на Т2 не дифференцирует клиентов.
