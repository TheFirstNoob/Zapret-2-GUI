## 1. Контекст: зачем появился ASN-скан

Python/httpx; исходники разобраны — см. §5): таблица ~110 IP-проб по ASN

(nxdomain-спуфинг по ~40 UDP/DoH/DoT серверам).

Задача: повторить в нашем CDN-скане (вкладка «CDN-стабилизация»).

## 2. Хроника методологии (3 итерации — важно не откатить!)

1. **v1 (ошибка):** пробы шли ПОД работающим десинком пользователя.
   При включённом ipset-режиме пробные IP лежат в ipset-all → наш
   fake+multisplit применялся к белым SNI-пробам → результаты были смесью
   «ТСПУ + наш обман». Диагностировано сравнением: SYN DROP-набор из
   ASN-скана == «ломает»-набор из CDN A/B (DO/VLT/OVH/CV/CDN77/HE-01☆…).
2. **v2 (фикс, текущая):** скан сам глушит защиту (`_run_asn_scan`
   в server/server.py: kill + `asn_scan()` + сервис-осведомлённый
   `_restore_protection_after_naked`), конкурентность 4 (пачки SYN в один
   ASN будят антискан хостеров), curl с `-S` (текст ошибок не глушится),
   exit 28 классифицируется по stderr (CONNECT-фаза = SYN DROP; общий
   таймаут = TIMEOUT), «не отвечает» подтверждается повтором через 1.2 с
   (мобильная сеть теряет SYN рывками — см. §3).
3. **Критика пользователем принята:** ценность скана сейчас
   диагностическая (объяснить «почему X не работает»), НЕ самоулучшение.
   Решение: кнопка остаётся, но фича не рекламируется; список IP
   протухает (см. §4) — перед всерьёзным использованием обновлять из
   репо dpi-detector через jsDelivr.

## 3. Чистый замер на Т2 СПб (мобильный, 2026-09-06 вечер)

| Время | Инструмент | Условия | Результат |
|---|---|---|---|
| 26.08 | dpi-detector (скрин другого человека) | его сеть/условия | 97/110 OK (88%) |
| ~21:15 | наш CDN A/B (curl, домены) | ipset ON → OFF | «чинит 2, ломает 13» |
| ~21:45 | наш asn_scan (curl, чистый путь) | защита остановлена | 84/110 OK, 26 SYN DROP |
| ~22:05 | raw socket connect ×3 раунды | защита ВКЛ | «SYN DROP»-IP отвечают OK 3/3 |
| ~22:20 | dpi-detector 4.2.4 (`-t 34`) | winws2 hostlist (прозрачен) | **18/110 OK (16%)** |
| ~22:35 | наш asn_scan (curl, чистый путь) | защита остановлена | 66/110 OK, 44 SYN DROP |

**Выводы (важно!):**
- Один вечер — четыре разные картины. ТСПУ/транзит Т2 к этим ASN
  флапает по десяткам минут; одиночный скан = снимок, не приговор.
- Наши короткие curl-POST «проскальзывают» чаще (66–84 OK), их длинные
  keep-alive потоки режутся раньше (18 OK) — разные инструменты меряют
  разную экспозицию. Прямое сравнение цифр между инструментами
  некорректно; сравнивать надо динамику одного инструмента.
- SYN DROP-набор стабильно совпадает с ipset-«ломает»-набором при
  включённом ipset (п.1) — наш десинк реально ломает белый SNI-хендшейк
  к этим диапазонам (curl виснет в SSL_connect, а НЕ на SYN: проверено
  `curl -v` — «Trying IP...» затем schannel/ALPN и только потом таймаут;
  raw socket connect к тем же IP проходит мгновенно). Ярлык «SYN DROP»
  в нашем скане для этих случаев условен — это «TLS-фаза, сервер/ДПИ
  молчит». Не тратить время на «оживление» этих IP списком.
- CDN77 (169.150.x, 37.19.202.x) — флапает часами: OK → DROP → OK.
  Домен cdn.eso.org при этом резолвится в живые IP (в A/B «чинит»).

**Теория пользователя (НЕ проверена):** вечерняя деградация (97 → 18 OK
за один вечер) может быть реакцией ТСПУ на саму активность сканирования —
за вечер десятки проб в одни и те же диапазоны (CDN A/B + ASN-скан ×2 +
dpich-прогоны пользователя). Практические выводы: (а) не сканить часто
подряд; (б) после жирного скана первые замеры пессимистичны — делать
паузу час-два; (в) если утром всё вернётся к ~90 OK — теория
подтверждена, записать в ISP_NOTES как «ТСПУ временно режет сканеров».

## 5. dpi-detector (Runnin4ik/dpi-detector 4.2.4) — что это и как пользоваться

Python-тулза (httpx + rich TUI). Это «та самая программа со скриншотов»
(таблица 110 ASN + DNS-таблица). Позиционируется как анализатор
блокировок: показывает, ГДЕ и КАК режется трафик (по ASN, по DNS), но
ничего не чинит — для нас это эталонный внешний зонд и источник данных.

### Установка и запуск
- Готовый exe: `github.com/Runnin4ik/dpi-detector/releases`
  (распакованный 4.2.4 лежал в Downloads; запускается `dpi_detector.py`).
- Из исходников: `pip install "httpx[socks,http2]==0.28.1" h2 hpack
  socksio rich PyYAML` (см. requirements.txt репо), затем из папки
  программы:
  `python dpi_detector.py -t 34 --batch -o report.txt -c 30`
- Флаги CLI (app/args.py): `-t <цифры>` — какие тесты гнать (пропускает
  меню), `--batch` — без пауз/вопросов, `-o файл` — автосохранение
  отчёта, `-c N` — конкурентность (дефолт 50), `-p прокси`, `-d домен`
  (точечная проверка домена, можно несколько раз), `-v` — debug.
- Запускать НОРМАЛЬНЫМ python (не pythonw); TUI рисует rich-таблицы,
  отчёт пишется в `-o` файл.

### Тесты (цифры для -t, cli/input.py:38-45)
- `0` — инфо о сети/системе
- `1` — доступность DNS-серверов
- `2` — доступность доменов (TLS/HTTP) из domains.txt
- `3` — **TCP 16-20KB по 110 IP из tcp16.json** (та самая ASN-таблица)
- `4` — **белые SNI для ASN**: перебор whitelist_sni.txt (188 SNI) по
  заблокированным ASN; фаза 2 — «топ-3» найденных (на Т2 06.09 для
  AS396982 белый SNI не найден — все заблокированы)
- `5` — Telegram
- `6` — легенда статусов

### Ключевые параметры config.yml
TCP_BLOCK_MIN_KB=12 / TCP_BLOCK_MAX_KB=36 (полоса детекта обрыва),
FAT_DEFAULT_SNI=example.com, CONNECT_TIMEOUT=8 / READ_TIMEOUT=8
(FAT_READ_TIMEOUT=12), MAX_CONCURRENT=50; DNS_CHECK_DOMAINS и ~40
серверов UDP/DoH/DoT (их DNS_CHECK_DOMAINS: rutor.info, flibusta.is...).

### Методология пробы (tcp16_scanner.py)
Подключение к IP:443, chunked keep-alive 10×4KB, детект по первому чанку
за порогом (TCP_BLOCK_MIN_KB); классификация фаз (tcp_connect →
tls_handshake → sending_data → reading_data) через httpx event hooks;
ошибки — utils/error_classifier.py (Windows errno: WSAECONNRESET...).

### Файлы-данные (протухают!)
- `tcp16.json` — 110 IP-проб. IP, опубликованные на GitHub, нулятся/
  фильтруются хостерами за недели (наш чистый замер 06.09: 26 SYN DROP).
  Обновление: `cdn.jsdelivr.net/gh/Runnin4ik/dpi-detector@main/tcp16.json`.
- `whitelist_sni.txt` — 188 белых SNI (экосистема VK/2GIS/банки) —
  источник блобов для нас (см. make_blob.py).
- `domains.txt` — пул заблокированных ресурсов для теста 2.

### Наши копии и наш аналог
- `lists/cdn-asn-probes.json` (= их tcp16.json, скачан 06.09),
  `lists/whitelist-sni.txt`.
- Наш ASN-скан (кнопка на вкладке CDN) — упрощённый аналог их теста 3:
  один белый SNI (hcaptcha.com), один POST 32KB, конкурентность 4,
  чистый путь (защита останавливается). Их плюсы, которых нам не хватает:
  chunked-детект с фазами, перебор SNI по ASN (тест 4), DNS-таблица.
- Их слабое место: пиннед-IP протухают; их доменный подход из dpich

## 8. Сравнительный прогон: наш asn_scan vs dpi-detector 4.2.4 (07.09, Т2 моб.)

Оба инструмента прогнаны в узком окне на чистом пути и ПОД защитой (default+sochi_park, ipset OFF).

| Прогон | Их dpi-detector (-t 3, c=30) | Наш asn_scan |
|---|---|---|
| чистый путь (защита OFF) | 18/110 OK (16%) | 84/110 OK (26 SYN DROP) |
| под защитой (Sochi blob) | 18/110 OK (16%) | 84/110 OK (26 SYN DROP) — **идентично** |
| скорость | ~2-3 мин | 53с после оптимизации (было 192с) |

**Выводы:**
1. **Защита/блоб НЕ влияют на ASN-IP тест**: пробы с белым SNI (hcaptcha) не в наших hostlist — десинк их не трогает. Методика «чистого пути» и «под защитой» дают одно и то же.
2. **Разница 18 vs 84 — экспозиция, не качество**: их chunked keep-alive (10×4KB, read до 12с) ловит «ответ не пришёл» как TIMEOUT; наш single POST 32KB честно разделяет «поток ушёл целиком» (OK, даже без ответа) и «SYN не встал» (SYN DROP). Их TIMEOUT (85) — корзина, где «нет HTTP-сервера на IP:443» смешано с «DPI режет». Наша таксономия честнее.
3. **Единственный промах нашей экспозиции**: их DETECTED ×1 (chunked поймал обрыв, наш POST проскочил) — 1/110, не критично.
4. **Скорость починена**: `--connect-timeout 3` (SYN отваливается за 3с вместо 10) + concurrency 8 (у них 30-50, комьюнити терпит) — 192с → 53с.

**Доменный тест их тулзы (-t 2) под защитой+Sochi:** HTTP 33/36 OK (десинк пробивает даже RF-класс по HTTP), TLS 10/36 — TLS DROP на жёстком SNI-классе (tor/fb/x/media: multisplit светит реальный SNI — известное ограничение, не про блоб).

**Наша RATED-батарея: 11/11 OK и под sochi_park, и под google** — на текущей сети/времени блоб не дифференцирует (всё и так пробивается). Ценность блоба проявится на сетях, где google-фейк фингерпринтится DPI; селектор это и решает.

**Итог для пользователя:** скрины комьюнити с «почти идеалом на Сочи» — другие сети/время/свежие IP; на Т2 моб. сейчас картина одинаковая в обеих тулзах (их 16%, наши 76% — разные метрики), и блоб не меняет наши 11/11 RATED.

## 9. Батарея SNI пробы (07.09, чистый путь, 110 IP × 5 SNI)

| SNI пробы | Результат | Комментарий |
|---|---|---|
| **example.com** (их дефолт) | **104/110 OK (94%)** | IANA-домен, в реестре быть не может |
| **www.sferum.ru** (VK) | 100/110 (91%) | российский «белый» |
| hcaptcha.com (наш прежний) | 84/110 (76%) | субоптимально |
| www.google.com | 79/110 (72%, +5 TLS RST) | гигант — фильтры плотнее |
| **rutracker.org (ЧЁРНЫЙ, контроль)** | **0/110 — все SYN DROP** | домен из реестра РКН: ТСПУ режет по SNI на TCP-уровне даже чистые VPS-диапазоны |

**Выводы:**
1. **SNI — переменная первого порядка**: контроль доказывает SNI-фильтрацию на SYN-фазе; «белые» SNI неравны (example 94% vs hcaptcha 76% vs google 72%).
2. **Два независимых фактора**: экспозиция (chunked vs single POST: их 18 vs наши 84-104) И SNI (hcaptcha 84 → example 104). Скрины «почти идеала» у людей — example.com (их дефолт), не «магия Сочи».
3. **Практика**: дефолт ASN_SNI сменён на example.com (в реестре быть не может, максимум пропускания). `asn_scan(..., sni=...)` теперь параметризован — можно сравнивать SNI в GUI.
4. ТСПУ по-разному смотрит на «белые» SNI: для диагностики «где режутся подсети» example.com — самый честный зонд; hcaptcha/google показывают «сверхреалистичную» картину (дополнительные SNI-фильтры).
