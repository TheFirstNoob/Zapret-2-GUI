# Стратегический роадмап: модификаторы, протокол валидации, границы

> **Обновлено: 2026-09-06.** Основан на дайджесте manual.md v1.0.2, инвентаре
> lua-движка, разборе комьюнити-репо и STRATEGY_TRIALS. Читается вместе с
> STRATEGY_GUIDE и STRATEGY_TRIALS.

## 0. Пять принципов (обсуждено и утверждено)

1. **Один параметр — одна гипотеза о DPI.** Параметр без гипотезы «почему это
   может пробить» не добавляется. Больше правил ≠ лучше: лишний параметр —
   это микрозадержка, размер пакета и риск нестабильности.
2. **Модификатор встраивается в вызов при построении пресета**, а не
   дописывается в конец цепочки. Если база уже пробивает, дописанный в конец
   модификатор неотличим от нуля и лишь добавляет overhead (подтверждено:
   tcp_md5 в конце — мусор и задержка).
3. **Пользователь не получает модификаторы.** Пользователь меняет только
   безопасное: стратегию (пресет), свои списки, тогглы. Параметры внутри
   пресетов — зона разработчиков. Вариация для пользователя = выбор стратегии.
4. **Кандидат обязан пройти CDN A/B.** CDN-класс критичен (Steam/Akamai,
   googleapis, Discord Media). Правило из испытаний: не «пробивает больше
   всех», а «пробивает цели и не глушит то, что живо без десинка».
5. **Сегментация `--new` — правильная архитектура пресета.** Единый пресет
   «по портам и доменам сразу» не работает в принципе: всегда будет
   «одно пробили — второе заглушили — третье не пробили». Поэтому каждый
   сервис/семейство (Discord Voice, Discord Media TCP, Discord TLS,
   Google TLS, General TCP, QUIC Google, QUIC General) живёт в своём
   блоке со своими фильтрами и своей цепочкой — популярное чинится точечно.
   Следствия: (а) кандидат меняет только целевой блок; (б) смешивание
   победителей по блокам — легитимный финал (так работает build_custom).

## 1. Механика модификаторов (гипотезы, условия, цена)

Формат: механизм → когда помогает → когда бесполезен/вредит → цена.

### tcp_md5 (RFC 2385, опция 19)
- **Механизм:** легитимная транспортная сигнатура (BGP-сессии). DPI не может
  валидировать подпись (секрет только у endpoints) и часто пропускает такие
  пакеты как служебные либо ломается его парсер редкой опции. Сервер без
  настроенного секрета игнорирует опцию.
- **Помогает:** DPI, фингерпринтящий «обычный» TLS по набору TCP-опций.
- **Бесполезен:** где режут по содержимому/seq-валидности; на базе, которая
  и так пробила (п.0.2).
- **Цена:** +18 байт к опциям каждого фейк-пакета; часть старых middleboxes
  дропает неизвестную опцию.
- **Статус у нас:** подтверждён полигоном (pkt_verify: 24 пакета с MD5,
  SNI фейка виден) и 100% чистым окном на Т2 (tcpmd5-fake). Кандидат №1.

### ip_autottl (авто-TTL)
- **Механизм:** фейк должен дожить до DPI и умереть до сервера. autottl
  считает дистанцию до сервера из входящего TTL и кладёт фейковый TTL в
  диапазон `delta,min-max` — сам подстраивается под глубину ТСПУ провайдера.
  Фиксированный ip_ttl так не умеет.
- **Помогает:** fake-зависимые DPI, где фиксированный TTL не угадан.
- **Вредит:** при неудачном delta фейк доходит до сервера (мусор в потоке).
  Стандарт «community»: `ip_autottl=-2,3-20` / `-1,3-20`.
- **Цена:** ≈ нулевая (кэш per-connection).

### tcp_ts / tcp_ts_up
- **Механизм:** DPI, валидирующий монотонность TCP timestamps, дропает фейк
  с TS в прошлом. `tcp_ts_up` поднимает TS первой опцией (нужен Linux-сервер
  с TS; наши цели — не Linux-стек, редко применимо).
- **Требует:** включённые timestamps — `tcp_timestamps.enable_for_engine()`
  уже делает это при каждом старте.

### tls_mod: rnd / rndsni / dupsid / sni=
- **Механизм:** статический блоб (один и тот же google-ClientHello) —
  статический же фингерпринт: DPI запоминает «фейковый ClientHello» и режет
  его. `rndsni` — случайный SNI на каждый фейк, `dupsid` — session_id из
  настоящего hello, `rnd` — случайные поля.
- **Противопоказание:** если DPI работает по белому списку SNI, случайный
  SNI сам станет признаком → нужен «белый» блоб (google/max), т.е. это
  противоположные техники для противоположных типов DPI. Выбор зависит от
  типа DPI, не «чем агрессивнее тем лучше».
- **Статус:** cand-rndsni 84.6% на Т2 (механика рабочая); побочка — меняет
  блоб глобально для всех фейковых вызовов пресета.

### seqovl (+pattern)
- **Механизм:** «скрытый фейк»: мусор-префикс уходит слева за окно по seq,
  DPI (не следящий за окном) читает мусор как начало данных, сервер отбрасывает.
  Паттерн делаем «белым» (google_tls) — уже так в default.

### ipfrag
- **Механизм:** фрагментация на IP-уровне; DPI без IP-reassembly не видит SNI.
  `ipfrag_disorder` — второй фрагмент первым. UDP: pos кратен 8.
- **Риск:** часть сетей режет фрагментированный трафик вообще; NAT-глюки.
  В GUI не используется ни разу — только как exp-кандидат.

### syndata (+send:repeats=2) — zero-phase
- **Механизм:** ClientHello внутри SYN; DPI видит «данные» до handshake и
  сбрасывает/зависает классификацию; соединение идёт чистым.
- **Ограничение:** без `--ipcache-hostname` + DNS-перехвата не работает
  точечно по хостлистам (на первом пакете hostname неизвестен). На Т2
  «вслепую» отсеян (30–46%). Кандидат для других сетей — только отдельным
  пресетом, не в default.

### udplen
- **Механизм:** раздувание UDP-пейлоада на N байт; UDP-сегментации нет,
  DPI с жёсткой привязкой к длине/офсетам (Discord voice) промахивается.
- **Место:** только в блоке Discord Voice (тоггл уже изолирует его).
  Цена ≈ нулевая.

## 2. Протокол валидации кандидата (обязательный)

Кандидат = копия default с ОДНИМ изменением (контроль переменных).
Пути: `presets/cand-*.txt` (скрыты из GUI `_ui_presets`).

1. **Fail-набор:** тестировать на доменах, которые база НЕ пробивает
   (тестер умеет: blocked_domains лучшей стратегии). На чистом окне
   разницу кандидат/база измерить нельзя (п.0.2).
2. **Полигон (pkt_verify):** механическая проверка, что параметр реально
   вышел в пакеты (MD5-kind 19, TTL, размер), а не «перекрыт другим
   модификатором» и не «мусор по 200/000».
3. **CDN A/B:** прогон CDN-класса (fix/break) до/после. Кандидат, который
   чинит цель, но добавляет DET в fix-классе — отклоняется (п.0.4).
4. **Окно стабильности:** 2+ сети, время наблюдения. Одиночная сеть = пометка
   «для сетей, где X», не дистрибутив.
5. **Результат → строка в STRATEGY_TRIALS.** Проигравший пресет не удаляем.

## 3. Кейс «два ПК в одной Wi-Fi глушили друг друга» (Zapret 1)

**Симптом:** одна Wi-Fi-сеть, два ПК; на каждом обход по отдельности работал,
совместно — нет; «лечилось» разными стратегиями на машинах. Единичный, но
повторяющийся кейс.

**Разбор механики:**
1. **Локально машины interference дать не могут.** WinDivert перехватывает
   только трафик своего хоста; LAN-трафик соседа отсечён `--wf-filter-lan=1`
   (неглобальные IP не перехватываются). На L2/L3 ПК друг друга не видят.
2. **Реальная точка взаимодействия — ТСПУ/абонентский уровень.** Оба ПК за
   одним NAT = один публичный IP. Часть DPI-логики ведёт пер-IP (абонентскую)
   статистику: аномальные пакеты (фейки с MD5/странными TTL/повторами) с
   двух машин суммируются и меняют классификацию всего адреса. Две разные
   агрессивные стратегии взаимно «портят» статистику друг друга — отсюда
   эффект «глушили сами себя» и то, что помогало расселение по стратегиям
   (меньше суммарной агрессии / разные сигнатуры).
3. **Вторичный фактор — домашний роутер:** фейки с очень низким TTL умирают
   на первом хопе (роутере); роутеры с встроенной «защитой»/DPI могут
   реагировать. Редко, но не ноль.

**Заплатка в GUI:** диагностический чек «Другие устройства в сети»
(`diagnostics._check_lan_peers`, ARP-кэш, всегда ok — информирует, не пугает):
если в сети есть другие хосты и обход нестабилен — подсказка «включите на
всех ПК одну и ту же стратегию; для провайдера это один адрес». Правильная
практика для общей сети: **одна и та же, наименее агрессивная из рабочих
стратегий на всех машинах**.

## 4b. Запасной план против «гонки репитов» (2026-09-10) 🚨

**Проблема:** `repeats=N` — тупиковая гонка. `rawsend_rep()` (darkmagic.c:2037)
шлёт байт-в-байт копии одного пакета (manual:2127 «binary-identical...
No changes made, including to ip_id»). DPI рано или поздно научится маркировать
«всплеск одинаковых пакетов» → нам придётся повышать repeats → пинг/трафик
растут, DPI снова подстраивается. Это эскалация, где выигрывает DPI.

**Не-репитные ортогональные механизмы (есть в движке v1.0.2):**

| Механизм | Суть | vs repeats | Цена |
|---|---|---|---|
| `tls_mod=rnd,dupsid` (на fake) | фейк из google-блоба со СЛУЧАЙНЫМИ полями + session_id из реального hello | нет паттерна «одинаковые пакеты» — DPI не маркирует статичный фейк | без repeats счётчик DPI не перегружаем |
| `tls_client_hello_clone` | клонирует РЕАЛЬНЫЙ ClientHello, подменяет SNI (`sni=...`) → фейк из настоящего hello, не из статического блоба | динамический фейк, DPI нечего маркировать | blob-myclone живёт в desync, not global |
| `oob` (URG) | пакет с URG + 1 байт out-of-band — DPI читает мусор | ноль повторов, ортогонален | требует старт с SYN |
| `syndata` | данные внутри SYN (ClientHello до handshake) | ноль повторов | требует ipcache-hostname + DNS-перехват (отложен) |
| `wssize` | переписывает TCP window на SYN-ACK — сбивает ассемблер DPI | ноль повторов | только SYN |
| `tcpseg` / `multidisorder` / `fakeddisorder` | режут/переставляют сегменты реального потока | меняют структуру, не дублируют | дроп сегментов |

**Статус (2026-09-10):** кандидаты `test-nodrop-mod`, `test-clone`, `test-oob`
созданы и валидны (dry-run OK), ждут live-прогона на Т2 (STRATEGY_TRIALS).
Если хоть один пробивает discord без repeats — это запасной план на случай,
когда ТСПУ начнёт детектить повторы.

## 5. Что НЕ делаем (и почему)

- IP-блоки (MTProto/Telegram, Facebook) — вне зоны движка; путь — hosts.txt.
- Break-класс CDN (DO/Hetzner/OVH/Vultr/BuyVM) — любой десинк вредит
  (STRATEGY_TRIALS, 2026-09-03). Не «стабилизируем».
- Комьюнити-пресеты вслепую — репо на API v0.9 (compat 5), в исходнике
  подтверждённые баги (ttl_ladder, seqovl_white, дубли http_methodeol_safe,
  instance_cutoff под оркестратором). Только порт отдельных техник с фиксом.
- wssize, oob, synack* — «крайние средства»/нишевые: только exp-, не для
  пользовательских пресетов (wssize режет скорость; oob требует старта с SYN
  и несовместим с сегментаторами).
- Вероятностные оркестраторы (cond_random) в пользовательских пресетах —
  нестабильность поведения для пользователя; зона экспериментов.
